## Demo 1: How does an xApp subscribe to E2 Node data, and what happens in the Near-RT RIC platform?

**Answer:**

An xApp subscribes to E2 Node data through a series of steps involving the Near-RT RIC platform. Here's how it works:

1. **Subscription Request**: The xApp sends an E2 related API: E2 Subscription request to the Near-RT RIC platform for a specific E2 Node and E2 request ID [3][4].

2. **Platform Processing**:
   - The Near-RT RIC platform checks if the xApp has an active subscription associated with the provided E2 Request ID [5].
   - If the request is valid, the Near-RT RIC platform updates its subscription records and modifies the distribution list(s) associated with the E2 Node ID and the RIC Request ID [3][4].
   - It then sends a notification to the relevant xApps via the SDL API [4].

3. **Notification Handling**:
   - Each relevant xApp receives a notification from the Near-RT RIC platform [4].
   - The xApp can decide whether to fetch the updated information from the SDL [4].

4. **Data Fetching** (if needed):
   - If the xApp decides to fetch the update, it sends a request to the Near-RT RIC platform to retrieve the updated E2NodeInfo or E2NodeList [4].
   - The Near-RT RIC platform responds with the requested information [4].

In summary, the Near-RT RIC platform handles the subscription request, updates its records, and notifies relevant xApps, while the xApp can choose to fetch the updated data if necessary. [3][4]

## Demo 2: What is the difference between the Non-RT RIC and the Near-RT RIC in terms of control loop timing and interfaces?

**Answer:**

The Non-RT RIC and the Near-RT RIC differ in their control loop timing and the interfaces they use:

- **Non-RT RIC**: Supports intelligent RAN optimization control loops with intervals greater than 1 second [3][5]. It communicates with the Near-RT RIC and other O-RAN elements via interfaces like A1, O1, and O2 [3].

- **Near-RT RIC**: Enables near real-time control and optimization of services and resources of E2 Nodes via fine-grained data collection and actions over the E2 interface with control loops in the order of 10 ms-1s [3][5]. It hosts xApps that use the E2 interface to collect near real-time information and provide value-added services [3].

These differences highlight that the Near-RT RIC is designed for faster, more immediate control and optimization compared to the Non-RT RIC, which operates on longer intervals.

## Demo 3: What is A1 enrichment information and who provides it?

**Answer:**

A1 enrichment information is information provided to an entity, in addition to the information that is generally available to it, in order to enhance the performance of its tasks [1]. It can be produced based on information from one or more sources, such as by relaying, combining, refining, or analyzing information from the input source(s) [2]. According to the context, SMO/Non-RT RIC framework acts as the A1-EI Producer, providing A1 enrichment information to the Near-RT RIC, which takes the role of A1-EI Consumer [2][3].

## Demo 4: In the O-RAN AI/ML workflow, what are the ML training host and the ML inference host, and where can they be deployed?

**Answer:**

In the O-RAN AI/ML workflow, the ML training host is the network function which hosts the training of the model, including both offline and online training [4]. The ML inference host is the network function which hosts the ML model during inference mode, often coinciding with the Actor [4].

Deployment-wise, the Non-RT RIC can serve as both the ML training host and the ML inference host [1][4]. Specifically:
- In Deployment Scenario 1.4, the SMO/Non-RT RIC acts as the ML training host for offline model training, while the Near-RT RIC serves as the ML training host for online learning and the ML inference host [1].
- The ML inference host is often the same as the Actor, which can be located in the Near-RT RIC [4].
